**Nota de instalación (09/11/2026):** `winget install PostgreSQL.PostgreSQL.18` **falla con 403**, porque EnterpriseDB rechaza el *User-Agent* de winget (`Download request status is not success. 0x80190193 : Prohibido (403)`).
```bash
curl -L -A "Mozilla/5.0" -o pg.zip \
  https://get.enterprisedb.com/postgresql/postgresql-18.6-5-windows-x64-binaries.zip
# extraer, y luego:
pgsql/bin/initdb  -D data -U postgres --pwfile=pw.txt -E UTF8 --locale=C
pgsql/bin/pg_ctl  -D data -l server.log -o "-p 5432" start
pgsql/bin/createdb -U postgres -h 127.0.0.1 eyes_test
```

Esto corrige la sección 2 de la planeación de integración, que daba `winget` como la vía simple.

Tres cosas se leen aquí:

**CP-NF-001 no se cumple, y el hallazgo es más grave que la latencia: con 50 usuarios la API

apunta a un límite compartido y no a un endpoint defectuoso.

### Explicación más probable (inferencia, no medición directa)

`app/core/database.py` configura `pool_size=10` y `max_overflow=20`: **30 conexiones como máximo**.
En QA cada consulta tarda ~1,2 s, casi todo en ir y volver a Oregón. Eso pone un techo aritmético
de throughput en torno a **30 ÷ 1,2 s ≈ 25 peticiones por segundo**. La corrida sostuvo 16,1/s con
8 % de fallas, que es justo lo que se espera de un sistema saturado cerca de su techo: las
peticiones esperan una conexión libre, se encolan y acaban agotando el tiempo de espera.

Aplicando la misma cuenta a producción, donde la consulta tarda 411 ms: 30 ÷ 0,41 s ≈ **73
peticiones por segundo**, unas cuatro veces más holgura. **Esto no significa que producción pase
CP-NF-001**: su p95 en reposo ya es 411 ms, la mitad del presupuesto, y bajo carga subiría. Pero sí
significa que el 8 % de errores es un síntoma del entorno de QA y no debe leerse como que la
aplicación falla con 50 usuarios reales.

### La API se recuperó sola

Tras la bajada, `GET /cursos` volvió a 1 437 ms, su línea base, **sin reiniciar el servicio**. Es el
criterio de recuperación que pide CP-NF-002.

### Qué se recomienda

1. **Registrar un solo hallazgo de rendimiento**, no uno por umbral incumplido, y enlazarlo a la
   decisión del PO sobre el criterio de aceptación en QA (ver la planeación de sistema).
2. **Medir en producción fuera de horario** si se quiere un número que sirva para aceptar o
   rechazar. La planeación lo prohíbe hoy; es una decisión del PO, no de QA.
3. **Revisar el tamaño del pool contra el límite de conexiones de Render.** Subir `max_overflow`
   solo ayuda si la base admite más conexiones; si no, empeora. Conviene confirmar el límite del
   plan antes de tocarlo.
4. **Reducir el trabajo por petición** es la única palanca que no depende de la infraestructura:
   hoy una consulta simple cuesta un viaje completo a Oregón, y cada endpoint que encadene varias
   los paga en serie.

### 5.1 BE-INF-4: no se pudo ni correr el preflight (hallazgo del 09/11/2026)

El despliegue de QA existe y está bien: `origin/developer` tiene `.github/workflows/developer_apieyeschool-q.yml`, que despliega a la Web App `apieyeschool-q` (slot `Production`, Python 3.11). Pero **no hay URL con la que llegar a QA**:

| Host probado | Resultado |
|---|---|
| `apieyeschool-q.azurewebsites.net` | **No existe en DNS** |
| `apieyeschool.azurewebsites.net` | No existe en DNS |
| `api-eyesschool.azurewebsites.net` | No existe en DNS |

Comprobado con `Resolve-DnsName`; desde el mismo equipo `github.com` y `get.enterprisedb.com` resuelven sin problema, así que no es un problema de red. La causa más probable es que Azure ya no asigna el nombre corto `<app>.azurewebsites.net` a las Web Apps nuevas, sino un **dominio regional** del tipo `<app>-<hash>.<región>-01.azurewebsites.net`.

**Consecuencia para el PR-01 y el PR-05:** el primer paso de BE-INF-4 no es revisar `DATABASE_URL`, sino **anotar las tres URLs reales** (Azure → cada Web App → Overview → *Default domain*): producción, QA y la Web App `api-eyesschool` de la decisión D-3. La planeación de integración ya decía «URL de la API de QA: pendiente de definir»; esto confirma que sigue pendiente y que es lo que bloquea todo lo demás.

`origin` tiene `main`, `developer`, `chore/calidad-seguridad` y `fix-accesos-padre`.
